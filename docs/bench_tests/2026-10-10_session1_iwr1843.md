## 10. Docker hw-mode smoke

- **Goal:** Smoke-test the Docker hw profile (see `docs/docker.md`). Only if time allows.
- **You do:**
  - `docker compose -f docker/app/compose.yaml build hw`
  - Export `RADAR_CLI=/dev/ttyACM0`, `RADAR_DATA=/dev/ttyACM1`, `HOST_UID`, `HOST_GID`, `DIALOUT_GID`.
  - `docker compose -f docker/app/compose.yaml --profile hw run --rm hw python -m radar_gui --host 100.83.97.21 --port 8090` (binds the tailnet IP).
- **Agent does:** Diagnoses the failure afterwards (read-only); the user ran the container.
- **Pass criteria:** In the GUI inside the container, Start configures the board, the firmware badge shows match, points stream, and Stop ends the session.
- **Status:** FAIL (root cause found: serial group plugdev 46 vs dialout 20). Retry with the gid taken from the device is pending the user's decision.
- **Result:**
  - The build and env setup worked.
  - The GUI was reachable over Tailscale on port 8090.
  - Clicking Start failed to start the radar. The container was removed with `--rm`, so its logs are lost; diagnosis is running.
  - Root cause: the container could not open `/dev/ttyACM1`. The error was `SerialStreamer: cannot open /dev/ttyACM1: Permission denied`, from `runs/gui/20261009T134303Z_1843_demo_tlv_default.cfg/driver.log`.
  - Why: on this host the serial nodes belong to group `plugdev` (gid 46), not `dialout` (gid 20). `DIALOUT_GID` from `getent group dialout` gave the container the wrong group. Native runs work because the user is in plugdev.
  - Interim workaround: `export DIALOUT_GID=$(stat -c %g /dev/ttyACM0)`.
  - Finding 1: Step 2 is too many commands. The user wants a `.env` file, or something similar, for ports and UID.
  - Finding 2: the system config did not appear in the Radar tab until the user clicked "Open in Run".
  - Finding 3: user configs that had never been opened in the GUI did not appear in the GUI's list.

## Open issues / follow-ups

- `bench_check.md` needs a `--cli-port` note.
- The shipped SAR JSONs hardcode `/dev/ttyACM0`, which is ambiguous when two XDS110s are plugged in.
- Minor margin: the first sensorStart after power-up took 74 ms against the hard 100 ms `cmd_timeout_ms` (later starts 5 ms). It passed; raise `cli.cmd_timeout_ms` in `IWR1843_SAR.json` only if a miss is ever seen. sensorStop (102-204 ms) is not an issue: it uses `stop_timeout_ms` (4000 ms).
- The core-24 Verify wording, "output equals", needs a complete-frames caveat (tail frame).

### GUI follow-ups (to Planner)

- Stale label: after saving, the link reads "Open in Run"; the tab is now called Radar.
- The driver's `sarStats` probe is rejected by the stock demo (expected "not recognized") but looks like a cfg error in the log.
- The radar rejects `bpmCfg -1 0 0 0` (streaming unaffected); check whether it comes from the user's cfg or the generator, and whether the 1843 stock demo supports it.
- Feature request: allow overwriting existing user configs when saving, for quick tuning.

- Cause of the two config-list findings: the frontend caches the config lists. The Radar tab only reloads on init, save, or "Open in Run". The Configure list loads once. A user `.cfg` that has no system JSON never appears in the Radar saved list. Fix: reload on each tab show and rename the link "Open in Radar".
